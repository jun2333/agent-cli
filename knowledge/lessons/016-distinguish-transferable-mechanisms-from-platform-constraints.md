# 参考云端 CLI 设计时，必须显式区分「可迁移机制」与「平台特有约束」

## 场景
需求里出现"参考 Claude Code / Codex 等主流 CLI 的设计"这类指示时（用户常见要求）。

## 问题
任务 005 调研了三家的上下文压缩与缓存机制，机制看起来可以直接搬，但底层平台前提完全不同，照搬会带来错误的工作量估计与错误方案：

| 维度 | 云端（Claude Code / Codex） | 本项目（本地 Ollama） |
|---|---|---|
| 缓存动机 | **成本**（读费率 ~10%） | **延迟**（prefill 8.6s → 0.2s，无计费） |
| 压缩执行方 | 有服务端能力：Claude Code 走 API 侧 auto-compaction；Codex 调 `POST /v1/responses/compact` 返回 AES 加密 blob | **没有**任何服务端压缩能力，摘要只能自己做 |
| 预算量级 | 200,000 tokens | 固定 **4096**（小 50 倍） |

量级差异会**放大机制差异**：云端"先剪枝工具结果"是小优化，本项目里一条 1000 行工具输出就能占满整个预算，所以"分层混合压缩"从可选变成必需。

## 解决方案
把调研产出组织成两段，并在文档里显式标注哪一段不可迁移：

1. **三家共性机制（可迁移）**：① 前缀复用 + 分层压缩 + 持久上下文外置的组合；② 压缩都是"先无损裁剪（剪枝/卸载工具结果）再 LLM 摘要"；③ 触发阈值倾向提前（60%~85%），不要等 95%；④ 持久规则不要指望压缩后还活着（应外置到 CLAUDE.md / AGENTS.md 这类文件）
2. **平台特有约束（不可迁移）**：逐条列出"云端有、本机没有"的能力（服务端压缩 API、缓存计费、200k 预算），并说明它如何改变方案
3. 把差异**直接写成设计约束**，而不是留在调研章节里当背景：由 ② 得出 D22（分层混合压缩）、由预算量级得出 D25（保真分层、工具结果优先牺牲）、由缓存动机得出 D23（前缀稳定硬约束）

## 判断准则
遇到"主流 CLI 这么做"的论据时先问一句：**这条机制成立的前提是什么？我们的平台满足这个前提吗？** 前提不满足时，机制本身要改写，而不是打折执行。
